## 3. القرارات المعمارية لقاعدة البيانات

### 3.1 المخططات (Schemas)

```text
NOONA_OWNER  ← يملك الجداول والحزم والسياسات (لا يتصل به أحد في التشغيل)
NOONA_APP    ← Parsing Schema لتطبيقات APEX و ORDS
               SELECT/DML على الجداول، SELECT فقط على الجداول التراكمية،
               EXECUTE على NOONA_SECURITY_PKG / NOONA_REFERENCE_PKG / NOONA_AUDIT_PKG
               لا يمنح NOONA_CTX_PKG (فلا يستطيع التطبيق تجاوز VPD)
```

### 3.2 نطاق ملكية كل جدول

| الرمز | المعنى | مثال | العزل |
|---|---|---|---|
| `G` | منصة عامة، بلا `TENANT_ID` | العملات، الدول، الباقات، SEC_USER | GRANTs والحزم |
| `TO` | منصة أو مؤسسة (`TENANT_ID` فارغ = قيمة منصة افتراضية) | القوائم المرجعية، أكواد الضرائب، الأدوار القياسية | VPD: قراءة المنصة + المؤسسة، تعديل المؤسسة فقط |
| `T` | مملوك للمؤسسة | الأطراف، الموظفون، المستندات | VPD صارم |
| `C` | مملوك للشركة (`TENANT_ID` + `COMPANY_ID` إلزاميان) | الفواتير، القيود، المخزون | VPD صارم + مفتاح مركب للشركة |

### 3.3 العزل متعدد الطبقات (Tenant Isolation by Design)

1. **Application Context** `NOONA_CTX`: يثبت Tenant/User/Membership/Company/Branch بعد التحقق من العضوية في `NOONA_SECURITY_PKG.establish_session`، ولا يقرأ من Page Items.
2. **VPD**: كل جدول `T`/`C` عليه سياسة `NP_TENANT_ISOLATION` (SELECT/INSERT/UPDATE/DELETE مع `update_check`). غياب السياق = `1 = 0`.
3. **مفاتيح أجنبية مركبة**: كل جدول أب مملوك للمؤسسة يحمل `UNIQUE (TENANT_ID, ID)`، وكل ابن يشير إليه بـ `(TENANT_ID, X_ID)`. يستحيل ربط سجل بسجل من مؤسسة أخرى حتى لو تم تجاوز VPD.
4. **Triggers**: تملأ `TENANT_ID` من السياق، وتمنع تغييره بعد الإنشاء (`NOONA-SEC-001`).
5. **APEX Authorization + فحص الحزم** (المرحلة التالية).

### 3.4 المفاتيح والأنواع

| القرار | التطبيق |
|---|---|
| المفتاح الأساسي | `ID NUMBER(19) GENERATED BY DEFAULT ON NULL AS IDENTITY`، يسمح بنقل Tenant بمعرفاته إلى PDB مخصصة |
| معرف خارجي | `PUBLIC_ID RAW(16) DEFAULT SYS_GUID()` للروابط و APIs |
| النصوص | `VARCHAR2(n CHAR)` لدعم العربية |
| المبالغ | `NUMBER(24,6)`، والتقريب حسب `REF_CURRENCY.DECIMAL_PLACES` (0/2/3) |
| أسعار الصرف | `NUMBER(28,12)` وتثبت داخل المعاملة |
| الأوقات | `TIMESTAMP WITH LOCAL TIME ZONE`. يوصى بضبط `DBTIMEZONE = '+00:00'`، ويعرض APEX الوقت بمنطقة المستخدم |
| المنطقي | `CHAR(1)` بقيد `Y/N` (لا يوجد BOOLEAN في SQL على 21c) |
| JSON | `CLOB CHECK (col IS JSON)` (متوافق مع APEX ومع إعدادات COMPATIBLE المختلفة) |
| الحالات | `STATUS_CODE` بقيد `CHECK` لدورات الحياة المعتمدة في الوثيقة. القيم القابلة للتخصيص في `REF_LOOKUP_VALUE` (BR-008) |
| التزامن | `ROW_VERSION` يزيد في كل تعديل |
| الحذف | لا `ON DELETE CASCADE` إطلاقاً. البيانات المالية تُلغى أو تُعكس، والسجلات التراكمية لا تقبل UPDATE/DELETE |
| المفاتيح الفريدة المشروطة | فهارس فريدة دالية لمفاتيح Idempotency الاختيارية (`NUKn`) |

### 3.5 الجداول التراكمية (Append-only)

سجلات التدقيق والأحداث والقرارات (`AUD_EVENT`، `WF_TASK_ACTION`، `DLG_EXERCISE_EVENT`، `COR_RECIPIENT_EVENT`، `HSP_FOLIO_LINE`...) تحميها Triggers ترفض UPDATE/DELETE (`NOONA-AUD-001`)، ولا يسمح بالحذف إلا في `PURGE_MODE` عبر إجراء الإتلاف المعتمد. `AUD_EVENT` يحمل سلسلة SHA-256 (`PREV_HASH` → `ROW_HASH`) ويمكن التحقق منها عبر `NOONA_AUDIT_PKG.verify_chain`.

### 3.6 الأنماط المشتركة

- **الربط العام بالكيانات:** `ENTITY_TYPE` يشير إلى `REF_ENTITY_TYPE` (لا قيم حرة)، و `ENTITY_ID` يتحقق منه خادمياً (المرحلة 10).
- **القوس الحصري:** العناوين وجهات الاتصال تستخدم أعمدة FK متعددة مع CHECK يسمح بواحد فقط بدلاً من نوع/معرف نصي.
- **Snapshots:** الفواتير تحفظ اسم العميل وعنوانه ورقمه الضريبي، والمهام تحفظ قرار حل المستلم، والقيود تحفظ رمز الحساب التاريخي.
- **الإصدارات غير القابلة للتعديل:** الباقات، تعريفات Workflow، قواعد الترحيل، قواعد الضرائب، BOM، قواعد الرواتب.
- **Idempotency و Outbox:** `API_OUTBOX` و `ACE_ACCOUNTING_EVENT.IDEMPOTENCY_KEY` و `COR_RECIPIENT.IDEMPOTENCY_KEY`...

## 5. تصميم تطبيقات Oracle APEX 24.2

### 5.1 تقسيم التطبيقات

| التطبيق | المستخدمون | المحتوى |
|---|---|---|
| **100 – NOONA Platform Console** | فريق NOONA | Tenants، الخلايا، الكتالوج، الاشتراكات، الفوترة، التراخيص، الإصدارات، الحوادث |
| **200 – NOONA ERP** (التطبيق الرئيسي) | مستخدمو المؤسسات | لوحة البداية، صندوق المهام والمراسلات، كل الوحدات حسب الاستحقاق |
| **300 – NOONA Self-Service** | الموظفون، المستأجرون، الموردون | الإجازات، القسائم، بلاغات الصيانة، كشوف الحساب |
| **400 – Front Desk / POS** | الاستقبال والكاشير | Unified Front Desk Room Rack، شاشة البيع السريع |

كل التطبيقات تستخدم `NOONA_APP` كـ Parsing Schema، وتشترك في Theme واحد (Universal Theme + NOONA Design System) عبر تطبيق Master للـ Shared Components.

### 5.2 دورة الطلب الآمنة في APEX

```text
Authentication (APEX Accounts / Entra ID / SAML / OIDC)
   └─ Post-Authentication: NOONA_SECURITY_PKG.establish_session(:APP_USER, :P0_TENANT_ID_FROM_LOGIN, ...)
Initialization PL/SQL Code (كل طلب):
   NOONA_SECURITY_PKG.attach_session(:APP_SESSION, :APP_USER);
Cleanup PL/SQL Code (كل طلب):
   NOONA_SECURITY_PKG.detach_session;      -- يمنع وراثة السياق عبر Pool
Logout: NOONA_SECURITY_PKG.end_session;
```

- **Authorization Schemes** تستدعي `NOONA_SECURITY_PKG.has_permission('SAL_INVOICE.APPROVE')` على مستوى الصفحة والمنطقة والزر والعملية، ثم يعاد الفحص داخل الحزمة. إخفاء عنصر القائمة ليس حماية.
- **Build Options / Entitlements:** تظهر الوحدات حسب `PLT_ENTITLEMENT`.
- `TENANT_ID` لا يظهر في أي Page Item قابل للتعديل.

## 6. الذكاء الاصطناعي لاحقاً على 21c

الوثيقة المرجعية تستهدف Oracle AI Database 26ai، بينما التنفيذ الآن على 21c. لذلك:

- جداول الحزمة 24 (`AI_*`) جاهزة الآن، و `AI_DOCUMENT_CHUNK.EMBEDDING` مخزن كـ `BLOB` (مصفوفة FLOAT32).
- البحث المتجهي على 21c يتم خارج قاعدة البيانات أو بحساب التشابه في PL/SQL لكميات صغيرة، ويعتمد البحث النصي على **Oracle Text** على `DMS_OCR_TEXT` و `AI_DOCUMENT_CHUNK.CHUNK_TEXT`.
- عند الترقية إلى 23ai/26ai يضاف عمود `VECTOR(n, FLOAT32)` ويعبأ من `EMBEDDING`، ثم ينشأ `VECTOR INDEX`، دون تغيير بقية النموذج.
- الاستدعاء من APEX 24.2 عبر **Generative AI Services** (OCI GenAI / OpenAI-compatible) مع فحص `AI_TENANT_SETTING` و `has_permission` قبل كل استرجاع (BR-005).

## 7. التوصيات التشغيلية

1. `ALTER DATABASE SET TIME_ZONE = '+00:00'` قبل إنشاء البيانات.
2. تفعيل **TDE** و **Unified Auditing** على البيئات غير التطويرية.
3. التقسيم (Partitioning) مقترح عند الحاجة على: `AUD_EVENT`، `GL_JOURNAL_LINE`، `INV_TRANSACTION_LINE`، `COR_RECIPIENT`، `DMS_ACCESS_LOG`، `API_REQUEST_LOG` (Interval بالشهر/السنة)، بعد قياس الأحجام وحسب الترخيص.
4. فهرس **Oracle Text** على `DMS_OCR_TEXT.EXTRACTED_TEXT` للبحث العربي.
5. Job يومي لإعادة بناء `GL_BALANCE` و `INV_ONHAND` من الحركات ومطابقتها (مصدر الحقيقة هو الحركات).

## 8. كيف تعدّل التصميم

لا تعدل ملفات `db/ddl` أو `docs/erd` أو `docs/data-dictionary` يدوياً. عدّل ملف الحزمة في `tools/model/` ثم:

```bash
python3 tools/generate.py
```

يعيد التوليد DDL والـTriggers وسياسات VPD والصلاحيات والـERD والقاموس معاً، فتبقى كلها متطابقة. أي تغيير على قاعدة بيانات منشورة يكتب كسكربت Migration مرقم ويسجل في `DEP_SCHEMA_MIGRATION`.
