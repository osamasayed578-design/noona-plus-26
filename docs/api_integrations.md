# واجهات REST والتكاملات

المنطق في `NOONA_API_PKG` (الواجهة والأحداث والرسائل) و`NOONA_CONN_PKG` (الموصلات). الشاشات في **إدارة المؤسسة (123)** تحت
«التكاملات وواجهات API»، والمطابقة البنكية في **المالية (127)**. التحديث: `db/upgrade_33_api.sql` ثم `db/ords/api_v1.sql` بحساب
NOONA_APP. الاختبار: `db/tests/test_api.sql` (85 اختباراً).

## الواجهة (ORDS)
- العنوان: `https://<الخادم>/ords/noona/v1/` — التوصيف: `GET /openapi.json` (OpenAPI 3، يستورد في Postman وSwagger).
- **عميل API** لكل نظام خارجي: ينشأ له حساب خدمة (مستخدم من نوع تكامل بلا كلمة مرور) بدور وشركة، فتطبق الصلاحيات وعزل البيانات
  كأي مستخدم. السر يعرض مرة واحدة ويحفظ Hash فقط؛ «إصدار سر جديد» يلغي القديم ورموزه.
- **الدخول**: `POST /token` بـ `client_id` و`client_secret` ← رمز Bearer صالح لمدة العميل (افتراضياً 60 دقيقة).
- **الحماية**: حد طلبات بالدقيقة لكل عميل (429)، قائمة IP اختيارية تقبل `*`، صلاحية لكل نقطة نهاية (403)، وسجل لكل طلب
  (الوقت، النقطة، الحالة، المدة، IP، كود الخطأ) بلا جسم الطلب أو الأسرار.
- **منع التكرار**: إنشاء الفواتير والتحصيل يتطلب `Idempotency-Key`؛ نفس المفتاح بنفس الطلب يعيد نفس الرد دون مستند جديد،
  وبطلب مختلف يرفض (409). المفاتيح تحفظ 7 أيام.
- **الأخطاء**: `{"error":{"code","message","requestId"}}` — 400 طلب غير صالح، 401، 403، 404، 409، 422 قاعدة عمل (كود NOONA)، 429.

| النقطة | الوصف |
|---|---|
| `GET /ping` | فحص الاتصال وهوية العميل |
| `GET/POST /customers`، `GET /customers/{id}` | العملاء (مع الرصيد) |
| `GET/POST /suppliers`، `GET /suppliers/{id}` | الموردون |
| `GET/POST /items`، `GET /items/{id}` | الأصناف (مع الكمية المتاحة)؛ البحث بالباركود عبر `sku` في الأسطر |
| `GET/POST /sales-invoices`، `GET /sales-invoices/{id}` | فواتير المبيعات (ترحل وتدخل الفوترة الإلكترونية؛ القراءة تعيد حالتها ورمز QR) |
| `POST /receipts` | تحصيل مع تخصيص على الفواتير |
| `GET/POST /purchase-invoices` | فواتير الموردين |
| `GET /accounts`، `GET /trial-balance?to=` | دليل الحسابات وميزان المراجعة |
| `GET /units` | الوحدات العقارية وحالتها |
| `POST /orders` | طلب متجر إلكتروني (انظر الموصلات) |
| `GET/POST /webhooks`، `POST /webhooks/{id}` (اختبار)، `DELETE /webhooks/{id}` | اشتراكات العميل |

معاملات القوائم: `q` بحث، `limit` (حتى 500) و`offset`، `from` و`to` للتواريخ، `status` أو `customer` للتصفية.

## الأحداث والـWebhooks
- الأحداث: ترحيل فاتورة مبيعات، تحصيل من عميل، ترحيل فاتورة مورد، توقيع عقد بيع وحدة، تفعيل عقد إيجار، طلب متجر.
- تكتب في **الصندوق الصادر** ضمن نفس المعاملة (لا يرسل حدث لمعاملة تراجعت)، وفشل النشر لا يوقف العملية الأصلية.
- مهمة `NOONA_API_DISPATCH` (كل دقيقة) ترسل POST JSON بالترويسات `X-Noona-Event` و`X-Noona-Delivery` و`X-Noona-Timestamp`
  و`X-Noona-Signature: sha256=<HMAC-SHA256(السر، timestamp + "." + body)>`. المستقبل يعيد حساب التوقيع ويرفض الطلبات الأقدم من 5 دقائق.
- الفشل يعاد بعد 2، 4، 8... دقائق (حتى 6 ساعات) وحتى 10 محاولات ثم «متوقف»، ويمكن إعادته يدوياً. 50 فشلاً متتالياً توقف الاشتراك مؤقتاً.
- العناوين `test://ok` و`test://fail` تحاكي النجاح والفشل للتجربة دون شبكة.
- الإرسال الفعلي لعناوين خارجية يحتاج صلاحية شبكة من قاعدة البيانات (ACL) ومحفظة شهادات HTTPS، ينفذها مسؤول قاعدة البيانات:
  `DBMS_NETWORK_ACL_ADMIN.append_host_ace(host => 'api.partner.com', ace => xs$ace_type(privilege_list => xs$name_list('http'), principal_name => 'NOONA_OWNER', principal_type => xs_acl.ptype_db));`

## الرسائل (SMS / واتساب)
- قناة لكل شركة: **المحاكي** للتجربة أو **مزود REST** (العنوان، ترويسة التفويض، جسم الطلب بالمتغيرات `{{to}}` `{{text}}` `{{sender}}`).
  مفتاح المزود يحفظ مشفراً (AES-256).
- **قواعد** لكل حدث بنص قالب: `{{name}}` `{{number}}` `{{total}}` `{{company}}`، وترسل لجوال العميل المسجل عبر نفس الصندوق الصادر.

## الموصلات
- **استيراد CSV** للعملاء والموردين والأصناف: عناوين عربية أو إنجليزية، فاصلة أو فاصلة منقوطة، حقول بين علامات تنصيص. كل صف مستقل،
  والمكرر (نفس الاسم أو الرقم الضريبي أو رقم الصنف) والخاطئ يظهر في تقرير الاستيراد. حتى 5000 صف.
- **كشف الحساب البنكي** (المالية ← المطابقة البنكية): التاريخ والمبلغ أو مدين/دائن، المرجع، البيان. الملف نفسه لا يستورد مرتين والأسطر
  المكررة تتجاهل. المطابقة التلقائية تقترح لكل سطر حركة البنك بنفس المبلغ والاتجاه خلال ±3 أيام (المرجع يرفع الثقة)، ثم تعتمد أو
  ترفض أو يتجاهل السطر (رسوم بنكية مثلاً). الاعتماد يعلم الحركة «مسواة»، والكشف «مسوى» عند اكتمال أسطره.
- **طلبات المتجر الإلكتروني** (`POST /orders`): `orderId` مرة واحدة فقط (الإرسال المكرر يعيد النتيجة السابقة)، العميل يطابق بالجوال
  أو ينشأ، الأصناف بالـSKU أو الباركود، الشحن سطر مستقل، الأسعار شاملة الضريبة افتراضياً. الطلب يصبح فاتورة مبيعات مرحلة، وإن كان
  `paid: true` يحصل على `place` (مثل `BANK:3`).
